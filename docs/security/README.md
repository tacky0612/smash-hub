# セキュリティポリシー

> ステータス: **Draft**。脆弱性の報告方法はリポジトリ直下の [SECURITY.md](../../SECURITY.md) を参照してください。

このポリシーは Smash-hub の **ソフトウェア（開発プロジェクト）** と、Smash-hub を使って **インスタンスを運営するすべての運営者** に適用されます。

## 基本原則

### 1. 持たないものは漏れない（データ最小化）

**Smash-hub のインスタンスは利用者の個人情報を保持しません。**
氏名・メールアドレス・電話番号・住所・パスワード・外部サービスのアカウント名などを受け取らず、保存しません。
ログインは外部の認証プロバイダーに任せ、インスタンスは「そのプロバイダーで同じ人がログインしたこと」を識別できる最小限の情報だけを、元に戻せない形で保持します。
詳しくは [データ保護](data-protection.md) を参照してください。

### 2. 運営者を信頼しなくても検証できる

連合では、他のインスタンスの運営者が誠実であるとは限りません。
対戦記録は両プレイヤーの署名で、ログはハッシュチェーンとインスタンス署名で守り、受け取った側が検証します（→ [連合プロトコル](../architecture/federation.md)）。

### 3. 運用者に高度なセキュリティ運用を求めない

個人運営のインスタンスでも安全に動かせるよう、**安全な設定を初期値にします**。
認証基盤は自前で運用せず、無料で使える外部プロバイダーに任せます（→ [認証](authentication.md)）。

### 4. 安全側に倒す

検証に失敗したデータは取り込まない。判断に迷う入力は拒否する。権限は必要最小限にする。

## ソフトウェアのセキュリティ要件

### 4.1 認証・セッション

- 認証は外部プロバイダーの OAuth 2.0 / OpenID Connect で行う。**パスワード認証は実装しない。**
- 認可コードフロー + PKCE を使い、`state`（と OIDC の `nonce`）を必ず検証する。
- セッションはサーバー側で管理し、Cookie は `HttpOnly`・`Secure`・`SameSite=Lax` 以上とする。トークンをブラウザの `localStorage` 等に保存しない。
- 状態を変更するリクエストには CSRF 対策を行う。
- 運営者向けの管理機能は、一般の利用者と分けた権限で保護する。

### 4.2 鍵と秘密情報

| 秘密情報 | 保管場所 | 扱い |
|---|---|---|
| アカウントの署名鍵（秘密鍵） | インスタンスの DB | 鍵暗号化鍵（KEK）で暗号化して保存する |
| リカバリーキー（秘密鍵） | **利用者の手元のみ** | ブラウザ内で生成し、インスタンスには公開鍵だけを送る |
| インスタンスの署名鍵 | 設定（環境変数・シークレットファイル） | DB とは別に保管する |
| 識別子ハッシュ用のペッパー | 設定（環境変数・シークレットファイル） | DB とは別に保管する（→ [データ保護](data-protection.md)） |
| 外部プロバイダーのクライアントシークレット | 設定（環境変数・シークレットファイル） | リポジトリに含めない |

- 秘密情報をソースコード・ログ・エラーメッセージ・連合で配信するデータに含めない。
- 署名は Ed25519 を第一候補とし、暗号処理は実績のあるライブラリを使う。自前で暗号を実装しない。

### 4.3 通信

- インスタンス間・ブラウザとインスタンス間の通信はすべて HTTPS とする（HTTP は受け付けない）。
- インスタンス間のリクエストにはインスタンス署名を付け、受信側で検証する（ヘッダーの形式は [連合プロトコル](../architecture/federation.md) の 11.3。将来 HTTP Message Signatures / RFC 9421 への移行を検討）。連合先は許可リスト（`PEERS`）で限定する。
- 再送攻撃を防ぐため、署名には日時を含め、許容範囲外のものは拒否する。

### 4.4 入力の扱い

- すべての外部入力（ブラウザ・他インスタンス）をスキーマで検証する。サイズ・件数の上限を設ける。
- 表示名などの利用者入力は、表示時にエスケープする（XSS 対策）。Content Security Policy を設定する。
- DB へのアクセスはパラメータ化したクエリで行う。
- ログイン・結果報告・連合 API などにレート制限を設ける。上限を超えたリクエストには `429 Too Many Requests` と `Retry-After` を返す。上限は次のとおり（[`ratelimit`](../../backend/internal/platform/ratelimit/ratelimit.go)）。ログイン中はアカウントごとに数えるため、同じ IP アドレスを共有する利用者（携帯回線など）が互いに影響しない。

  | 対象 | 数える単位 | 連続で受け付ける回数 | 回復の速さ |
  |---|---|---|---|
  | ログイン（`/api/auth/`） | IP アドレス | 10回 | 6秒に1回 |
  | 状態を変更する API（`GET` 以外の `/api/`） | アカウント（未ログインは IP アドレス） | 30回 | 1秒に1回 |
  | 参照する API（`GET` の `/api/`） | アカウント（未ログインは IP アドレス） | 120回 | 1秒に5回 |
  | インスタンス間の API（`/federation/`） | IP アドレス | 300回 | 1秒に10回 |

  IPv6 は /64 単位で数える。制限はインスタンス（プロセス）ごとのメモリ上で数え、ヘルスチェック（`/api/health`）は対象外とする。

### 4.5 ログ

- アクセスログには IP アドレスが含まれるため、不正対策に必要な最小限の期間（初期値 **14日**）で削除する。アクセスログはバックエンドが DB に記録し、保持期間を過ぎた行を定期的に削除する（期間は `ACCESS_LOG_RETENTION_DAYS` で変えられる）。frontend の nginx はアクセスログを出さない。
- アクセスログに記録するのは日時・IP アドレス・メソッド・パス・ステータス・処理時間だけとする。クエリ文字列（OAuth の認可コード等）・Cookie・ヘッダーは記録しない。
- ログに認証コード・トークン・セッション ID・秘密鍵を記録しない。
- IP アドレスを連合で共有しない。

## 開発プロジェクトのセキュリティ

- **依存関係** — ロックファイルを必ずコミットする。依存関係の脆弱性を自動で検知する（Dependabot 等）。新しい依存の追加は PR で理由を説明する。
- **シークレットの検知** — GitHub の secret scanning を有効にする。
- **ブランチ保護** — `main` への直接 push を禁止し、レビュー必須とする。
- **メンテナーのアカウント** — GitHub の二要素認証を必須とする。
- **リリース** — リリース成果物（コンテナイメージ等）は CI でビルドし、署名と SBOM の提供を検討する。
- **静的解析** — CI で lint と静的解析を実行する。

## 運営者に求めること

[サーバー運用者の約束事](../operations/server-covenant.md) に加え、次を推奨します。

- OS・ミドルウェア・Smash-hub を最新に保つ（セキュリティアップデートは速やかに適用する）
- SSH はパスワード認証を無効にし、鍵認証にする
- DB を外部ネットワークに公開しない
- 秘密情報（KEK・インスタンス鍵・ペッパー）のバックアップを DB とは別に、安全に保管する
- インシデントの際は [インシデント対応](incident-response.md) に従う
