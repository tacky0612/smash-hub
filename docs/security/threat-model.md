# 脅威モデル

> ステータス: **Draft**。設計の変更に合わせて更新します。

## 1. 守るもの

| 資産 | 失われると |
|---|---|
| 対戦記録の完全性 | レート・ランキングの信頼が失われる |
| 対戦記録の可用性 | 「記録を失わない」というプロジェクトの約束が果たせない |
| アカウントの乗っ取り耐性 | 他人になりすまして対戦・報告される |
| 利用者のプライバシー | 外部アカウントとの紐づけや行動の追跡をされる |
| インスタンスの稼働 | 利用者が対戦できない |

## 2. 想定する攻撃者

| 攻撃者 | 例 |
|---|---|
| 一般の利用者 | レート操作、虚偽報告、複数アカウント、嫌がらせ |
| 外部の攻撃者 | 脆弱性を突いた侵入、アカウント乗っ取り、DoS |
| 悪意あるインスタンス運営者 | 記録の捏造・改ざん・隠蔽、利用者データの悪用 |
| 侵害されたインスタンス | 秘密鍵・DB の漏えい、偽のログの配信 |

## 3. 脅威と対策

### 3.1 なりすまし（Spoofing）

| 脅威 | 対策 | 残るリスク |
|---|---|---|
| 他人のアカウントでログイン | 外部プロバイダー認証、PKCE・`state` 検証、`HttpOnly` Cookie | プロバイダー側のアカウント乗っ取り（利用者にプロバイダー側の二要素認証を推奨） |
| 他インスタンスのなりすまし | インスタンス署名付きリクエスト、HTTPS | — |
| 他人の名前で対戦記録を作る | 両プレイヤーの署名が必要 | 署名鍵を持つホームインスタンス運営者（→ 3.5） |

### 3.2 改ざん（Tampering）

| 脅威 | 対策 |
|---|---|
| 対戦記録の書き換え | 両者署名。改ざんされた記録は検証で拒否 |
| ログ途中の削除・差し替え | ハッシュチェーンとインスタンス署名 |
| 再配布時の改ざん | 元インスタンスの署名をそのまま検証するため、再配布者は改ざんできない |

### 3.3 否認（Repudiation）

| 脅威 | 対策 |
|---|---|
| 「その結果に同意していない」 | 両者の報告時の署名が記録に残る。報告が噛み合わない対戦は確定しない |
| 運営者の不正な無効化 | 無効化もイベントとしてログに残り、連合先から検証できる |

### 3.4 情報漏えい（Information Disclosure）

| 脅威 | 対策 |
|---|---|
| DB の漏えい | 個人情報を保持しない。識別子は HMAC でハッシュ化、ペッパーは DB と別保管。署名鍵は暗号化 |
| インスタンス間の名寄せ | インスタンスごとに異なるペッパー |
| ログからの漏えい | トークン・秘密情報をログに出さない。IP は短期間で削除 |

### 3.5 悪意ある運営者

現在の設計では、利用者の署名鍵をホームインスタンスが預かるため、**運営者は自インスタンスの利用者同士の架空の対戦記録を作れてしまいます**。これは「利用者に鍵の管理を強いない」こととのトレードオフです。

| 対策 | 時期 |
|---|---|
| 連合ポリシー（許可リスト）と[運用者の約束事](../operations/server-covenant.md) | Phase 3 |
| 異常検知（短期間の大量の記録、同一ペアの偏りなど）と、問題インスタンスの拒否・記録の除外 | Phase 4 |
| 利用者自身がブラウザ・端末で鍵を持ち、署名する方式（パスキー等）の選択肢 | 将来 |

### 3.6 サービス妨害（Denial of Service）

| 脅威 | 対策 |
|---|---|
| API への大量リクエスト | レート制限、リクエストサイズ上限 |
| 巨大・大量のログを送りつける | 取り込みのサイズ・件数上限、許可リスト方式の連合 |
| インスタンスの消失 | 記録の複製（ミラー・相互複製）、リカバリーキー |

### 3.7 権限昇格（Elevation of Privilege）

| 脅威 | 対策 |
|---|---|
| 一般利用者が管理機能を使う | 管理権限の分離、認可チェックを application 層のユースケースで必ず行う |
| 依存パッケージ経由の侵入 | 依存の最小化、脆弱性の自動検知、ロックファイル |

## 4. スコープ外

- 外部認証プロバイダー自体の脆弱性・障害
- 利用者の端末のマルウェア感染
- ゲーム内（オンライン対戦そのもの）での不正
