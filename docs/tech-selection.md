# 技術選定

> ステータス: **未決定**。このドキュメントは選定の基準と候補を整理するためのものです。決定は [ADR](adr/README.md) として記録します。

## 1. 選定基準

Smash-hub ならではの事情から、次の基準を重視します。

| 基準 | 理由 |
|---|---|
| **技術者でなくてもデプロイできること** | 運営者はスマブラのファンであり IT 技術者ではない。デプロイ方式の議論（[easy-deployment.md](operations/easy-deployment.md)）の結論を満たせること |
| **運用の軽さ** | 個人が安価な VPS 1台で運用できること。メモリ消費・依存ミドルウェアの少なさ・単一バイナリ/単一コンテナでのデプロイのしやすさ |
| **コントリビューターの集まりやすさ** | OSS として多くの人が読めて書ける言語・フレームワークであること |
| **長期の保守性** | 運営者や開発者が入れ替わっても保守できること。枯れていて、エコシステムが安定していること |
| **型安全性** | 署名・ハッシュ・レート計算など、誤りが記録の信頼性に直結する処理が多いため |
| **暗号ライブラリの品質** | Ed25519 署名・ハッシュ・正規化などを信頼できる実装で扱えること |
| **クリーンアーキテクチャとの相性** | インターフェースによる依存逆転、モジュール境界の静的チェックがしやすいこと |
| **決定的な数値計算** | レート計算を言語間・環境間で同じ結果にできること |

## 2. 検討対象と候補

### 2.1 バックエンド言語・フレームワーク

| 候補 | 長所 | 懸念 |
|---|---|---|
| TypeScript (Node.js / Bun) + NestJS / Hono 等 | フロントエンドと言語を揃えられ、コントリビューターが多い | ランタイムのメモリ消費、依存パッケージの多さ |
| Go | 単一バイナリで配布でき運用が軽い。暗号ライブラリが標準で充実 | DDD 的な表現（値オブジェクト・ジェネリクス）の書き味 |
| Rust (axum 等) | 高性能・省メモリ・強い型安全性 | 学習コストが高く、コントリビューターが集まりにくい可能性 |
| Kotlin / Java (Spring 等) | DDD・クリーンアーキテクチャの実践例が豊富 | JVM のメモリ消費 |
| Ruby on Rails | Mastodon と同じで運用知見がある | クリーンアーキテクチャとの相性、型安全性 |

### 2.2 フロントエンド

| 候補 | 長所 | 懸念 |
|---|---|---|
| React (+ Vite / Next.js) | コントリビューターが最も多い | SSR を使う場合の運用負担 |
| Vue (+ Vite / Nuxt) | 学習しやすく日本語情報が多い | — |
| Svelte / SvelteKit | 軽量・高速 | エコシステムが相対的に小さい |

静的配信できる構成（SPA または静的生成）を優先します。

### 2.3 データストア

| 候補 | 長所 | 懸念 |
|---|---|---|
| PostgreSQL | 信頼性・機能が十分、運用知見が多い | 小規模インスタンスでも別プロセスが必要 |
| SQLite | 単一ファイルで運用が最も軽い。バックアップが容易 | 書き込みの並行性。規模が大きくなった場合の移行 |

両方に対応できるよう、リポジトリ層で抽象化しておく案もあります。

### 2.4 その他

- リアルタイム通知: WebSocket / Server-Sent Events
- 認証: Discord（OAuth 2.0）/ Google（OpenID Connect）を直接利用（[ADR 0002](adr/0002-external-authentication-providers.md) で決定済み）
- 署名: Ed25519
- 正規化: JSON Canonicalization Scheme (RFC 8785) / CBOR (deterministic encoding)
- デプロイ: コンテナイメージ（Docker Compose で1コマンド起動）

## 3. 進め方

1. この基準と候補について Discussion で意見を募る。
2. 必要に応じて、有力候補で小さなプロトタイプ（署名付き対戦記録の作成・検証・レート計算）を作って比較する。
3. 決定を ADR として PR で提出し、レビューを経てマージする。
