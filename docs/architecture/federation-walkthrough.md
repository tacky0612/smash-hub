# 図解: 複数のインスタンスが勝敗記録とレートを共有する仕組み

> ステータス: **Draft**。現在の実装（Instance1・Instance2 の2台構成で動作確認済み）に基づく説明資料です。仕様の正は [SmashHubプロトコル](federation.md) です。

SmashHub では、独立した運営者が立てた複数のインスタンス（サーバー）が、**署名付きの勝敗記録をお互いに複製し合い**、それぞれが **同じ計算式でレートを計算し直す** ことで、どのインスタンスでも同じ戦績・同じレートを表示します。中央のサーバーはありません。

この仕組みで解決したいのは、次の3つです（→ [ビジョン](../vision.md)）。

| 課題 | この仕組みでの解決 |
|---|---|
| 1つのサイトが閉鎖すると、サービスも記録も消える | 記録を全インスタンスに複製する（→ 3・6） |
| サイトが乱立すると記録とレートがサイトごとに分かれ、サイトによって強さの水準がずれる | 全インスタンスが同じ記録から同じ計算式で **1つのレート（SmashHubレート）** を計算する（→ 4） |
| 利用者の少ないサイトでは、募集しても対戦相手が見つからない | 対戦募集をインスタンス間で配り合い、**別のインスタンスの利用者ともマッチングする**（→ 5） |

この資料では、その仕組みを次の順に図で説明します。

1. 全体像 — 何を共有し、何を共有しないか
2. 記録の作り方 — 両プレイヤーの署名とログ
3. 記録の共有 — pull 同期と検証
4. レートの共有 — 同じ記録から同じレートになる理由
5. インスタンスをまたぐ対戦 — 別のインスタンスの人と対戦する流れ
6. インスタンスが閉鎖したとき

---

## 1. 全体像

```mermaid
flowchart LR
  subgraph I1["Instance1（運営者 A）"]
    direction TB
    U1(("利用者")) --> W1["Web UI"]
    W1 --> B1["Backend"]
    B1 --> D1[("DB<br/>ローカルデータ<br/>＋ 共有データの複製")]
  end
  subgraph I2["Instance2（運営者 B）"]
    direction TB
    U2(("利用者")) --> W2["Web UI"]
    W2 --> B2["Backend"]
    B2 --> D2[("DB<br/>ローカルデータ<br/>＋ 共有データの複製")]
  end
  B1 <-- "SmashHubプロトコル（HTTPS）<br/>署名付きログの pull<br/>募集の配信・対戦の申し込み・報告の中継" --> B2
```

各インスタンスは自分の利用者だけを受け付け、自分の DB を持ちます。インスタンス同士は **SmashHubプロトコル** で通信します。

| データ | 例 | 共有するか |
|---|---|---|
| ローカルデータ | ログインの識別子ハッシュ、セッション、署名鍵（暗号化） | **しない**（そのインスタンスだけが持つ） |
| 一時データ | マッチング待ちの募集、進行中の対戦 | 必要な相手とだけ、その場限り |
| **共有データ** | アカウントの公開情報（ID・表示名）、**確定した勝敗記録** | **する**（全インスタンスに複製） |
| 派生データ | **レート**・ランキング | 共有しない。各インスタンスが共有データから **計算し直す** |

ポイントは、**レートそのものは送り合わない** ことです。送り合うのは「誰と誰が戦ってどちらが勝ったか」という署名付きの事実だけで、レートは各インスタンスがその事実から計算します。

## 2. 記録の作り方: 両プレイヤーの署名とログ

### 2.1 対戦が確定するまで

```mermaid
sequenceDiagram
  autonumber
  actor A as 太郎
  actor B as 花子
  participant H as ホストのインスタンス
  participant L as ホストのログ（追記専用）

  A->>H: 結果を報告「勝ち」
  Note over H: 太郎の鍵で「勝者 = 太郎」の<br/>対戦結果の内容に署名
  B->>H: 結果を報告「負け」
  Note over H: 花子の鍵で「勝者 = 太郎」の<br/>対戦結果の内容に署名
  H->>H: 2人の報告が一致 → 確定
  H->>L: MatchRecorded を追記<br/>（2人の署名 ＋ インスタンスの署名）
  H->>H: レートを計算し直す
```

- 「太郎の勝ち」と「花子の負け」は **同じ内容（勝者 = 太郎）への署名** になります。報告が一致したときだけ、2人分の署名がそろいます。
- 報告が食い違ったまま 24時間たった対戦や、2人とも「中止」と報告した対戦は、記録を作りません（レートも変わりません）。
- アカウントの ID は、そのアカウントの公開鍵から作った `did:key` です。**ID さえあれば誰でも署名を確かめられます。**

### 2.2 ログの構造

各インスタンスは、自分が確定させた記録を **追記専用ログ** に順番に書きます。

```mermaid
flowchart LR
  E1["seq 1<br/>AccountPublished<br/>太郎の公開情報<br/>prev: なし"]
  E2["seq 2<br/>AccountPublished<br/>次郎の公開情報<br/>prev: hash(seq 1)"]
  E3["seq 3<br/>MatchRecorded<br/>太郎 vs 花子<br/>prev: hash(seq 2)"]
  E4["seq 4<br/>MatchRecorded<br/>次郎 vs 幸子<br/>prev: hash(seq 3)"]
  E1 --> E2 --> E3 --> E4
```

| 仕組み | 守るもの |
|---|---|
| 各イベントにインスタンスの署名 | 発行元のなりすまし・内容の改ざん |
| `prev` に直前のイベントのハッシュ（ハッシュチェーン） | 途中のイベントの差し替え |
| `seq` の連番 | 途中のイベントの抜け落ち |
| `MatchRecorded` の中に両プレイヤーの署名 | インスタンスによる勝敗の書き換え |

ログは書き換えも削除もしません。取り消しが必要な場合は、取り消しのイベントを追記します（例: 記録のホストが発行する `MatchVoided`。→ [SmashHubプロトコル](federation.md) の「12.2 MatchVoided」）。

## 3. 記録の共有: pull 同期と検証

### 3.1 定期的に取りに行く

各インスタンスは、連合先のログを **自分から定期的に取りに行きます**（pull）。相手が一時的に止まっていても、復帰後に続きから取り直せば追いつけます。

```mermaid
sequenceDiagram
  autonumber
  participant I2 as Instance2
  participant I1 as Instance1

  Note over I2: 前回は seq 2 まで取り込み済み
  I2->>I1: GET /federation/log?since=2
  I1-->>I2: seq 3, 4 のイベント（署名済み）
  I2->>I2: 1件ずつ検証して取り込む
  I2->>I2: レートを計算し直す
  Note over I2: 次回は since=4 から
  I1->>I2: GET /federation/log?since=…（逆方向も同じ）
```

### 3.2 取り込む前に必ず検証する

取り込む側は、**送ってきたインスタンスを信用せずに**、次の順で確かめます。1つでも失敗したら、そのイベント以降は取り込みません。

```mermaid
flowchart TD
  S["連合先から届いたイベント"] --> C1{"発行元は<br/>許可リストの連合先か"}
  C1 -- いいえ --> R["取り込まない<br/>理由を記録して次回に再試行"]
  C1 -- はい --> C2{"インスタンスの署名は<br/>正しいか"}
  C2 -- いいえ --> R
  C2 -- はい --> C3{"seq が連続し<br/>prev が直前のハッシュと一致するか"}
  C3 -- いいえ --> R
  C3 -- はい --> C4{"イベントの種類"}
  C4 -- MatchRecorded --> C5{"両プレイヤーの署名が<br/>それぞれの did:key で正しいか<br/>ホストは発行元自身か"}
  C4 -- AccountPublished --> C6{"アカウント自身の鍵で<br/>署名されているか"}
  C5 -- いいえ --> R
  C6 -- いいえ --> R
  C5 -- はい --> OK["取り込む<br/>勝敗記録に追加"]
  C6 -- はい --> OK2["取り込む<br/>表示名などを更新"]
```

この検証により、悪意のあるインスタンスがいても、

- 他のインスタンスが作った記録を書き換えられない（署名が合わなくなる）
- 対戦していない人の勝敗を勝手に作れない（その人の鍵で署名できない）
- 他人のアカウントを名乗れない（アカウント自身の署名が必要）

ことが保証されます。

## 4. レートの共有: 同じ記録から同じレートになる理由

レートは、各インスタンスが **自分の手元に集まった勝敗記録** から計算します。計算の手順を全インスタンスで揃えているため、記録の集合が同じなら、どこで計算しても結果は同じになります。

```mermaid
flowchart LR
  subgraph IN["手元の勝敗記録（自分で確定させたもの ＋ 取り込んだもの）"]
    direction TB
    M1["太郎 vs 花子<br/>played_at 20:00<br/>（Instance1 で確定）"]
    M2["次郎 vs 幸子<br/>played_at 20:05<br/>（Instance2 で確定）"]
    M3["太郎 vs 幸子<br/>played_at 20:10<br/>（Instance1 で確定）"]
  end
  IN --> F["フィルタ<br/>今のシーズンの記録だけ<br/>取り込みの締め切り（7日）を過ぎた記録は除く"]
  F --> S["並べ替え<br/>played_at（対戦開始日時）の順<br/>同じ時刻なら記録 ID の順"]
  S --> C["スマメイト式を1件ずつ適用<br/>Δ = floor(16 + (敗者 − 勝者) ÷ 25)<br/>整数演算のみ"]
  C --> O["レート・ランキング"]
```

| 結果がずれる原因 | 対策 |
|---|---|
| 記録が届く順番がインスタンスごとに違う | 届いた順ではなく **対戦開始日時の順** に並べてから計算する |
| 何日も後に届いた古い記録で、過去のレートが変わり続ける | ホストがログに書いた日時と対戦開始日時の差が **7日を超える記録は計算に含めない**（どのインスタンスでも同じ値で判定できる） |
| 浮動小数点の計算誤差 | **整数演算だけ** で計算する |
| 相手のインスタンスが申告するレートの詐称 | 申告値は使わず、**自分で記録から計算した値** を使う（マッチングの判定も同じ） |

対戦直後は、まだ届いていない記録がある可能性があるため、そのときのレートは「暫定」です。通常は数秒で全インスタンスに行き渡るため、実際にはすぐに一致します（ローカルの2台構成では2秒間隔で取り込み）。

## 5. インスタンスをまたぐ対戦

Instance1 の太郎と Instance2 の花子が対戦する流れです。**先に待っていた側のインスタンスがホスト** になり、対戦の進行と記録の確定を担当します。

```mermaid
sequenceDiagram
  autonumber
  actor A as 太郎（Instance1 の利用者）
  participant I1 as Instance1（ホスト）
  participant I2 as Instance2
  actor B as 花子（Instance2 の利用者）

  rect rgba(215, 38, 61, 0.08)
  Note over A,B: マッチング
  A->>I1: 対戦相手を探す
  I1->>I1: 自分の利用者に相手がいない → 待機
  I1->>I2: 募集を配信（POST /federation/match-requests）
  Note over I1,I2: 待機中は配信し直して有効期限（30秒）を延ばす
  B->>I2: 対戦相手を探す
  I2->>I2: 自分の利用者に相手がいない<br/>配信された太郎の募集が条件に合う
  I2->>I1: 申し込み（POST /federation/match-claims）
  I1->>I1: 募集をロックして先着1件だけ承認<br/>対戦を作る（プレイヤー1 = 太郎）
  I1-->>I2: 対戦 ID
  I1->>I2: 配信の取り消し
  end

  rect rgba(37, 99, 235, 0.08)
  Note over A,B: 対戦ルーム
  A->>I1: 部屋 ID を入力
  B->>I2: 対戦ルームを開く
  I2->>I1: 対戦の状態を取得（GET /federation/matches/{id}）
  I1-->>I2: 部屋 ID・相手の情報
  I2-->>B: 部屋 ID を表示
  Note over A,B: ゲーム内の専用部屋で2本先取の対戦
  end

  rect rgba(31, 122, 58, 0.08)
  Note over A,B: 結果報告と確定
  A->>I1: 「勝ち」（太郎の鍵で署名）
  B->>I2: 「負け」
  I2->>I2: 花子の鍵で署名
  I2->>I1: 報告を中継（POST /federation/match-reports）
  I1->>I1: 花子の署名を検証 → 報告が一致して確定<br/>MatchRecorded をログに追記
  end

  rect rgba(180, 83, 9, 0.08)
  Note over A,B: 記録とレートの共有
  I2->>I1: ログを取り込む（GET /federation/log）
  I1-->>I2: MatchRecorded（2人の署名付き）
  I2->>I2: 検証して取り込み、レートを計算し直す
  Note over I1,I2: 両方のインスタンスで太郎 1516 / 花子 1484
  end
```

| 役割 | ホスト（Instance1） | 相手側のホーム（Instance2） |
|---|---|---|
| 対戦の状態（部屋 ID・報告） | 持つ（正） | 持たない。必要なときにホストから取得する |
| 花子の署名鍵 | 持たない | 持つ（花子の報告に署名する） |
| 記録の確定・ログへの追記 | する | しない（ホストのログから取り込む） |
| 報告の受け付け | 花子の分は、花子のホームからの中継だけを受け付ける | 花子の報告をホストへ中継する |

- インスタンス間のリクエストには **インスタンスの署名** を付け、相手を許可リスト（`PEERS`）で限定しています。
- 対戦記録を作れるのはホストだけです。他のインスタンスから記録そのものを送り込む API はありません。
- 自分のインスタンス内に条件に合う相手がいれば、インスタンスをまたがずにマッチします（その記録も同じようにログ経由で他のインスタンスへ共有されます）。

## 6. インスタンスが閉鎖したとき

記録は全インスタンスに複製されているため、1つのインスタンスがなくなっても、勝敗記録とレートは残ります。

```mermaid
flowchart LR
  subgraph BEFORE["閉鎖前"]
    direction TB
    A1["Instance1<br/>記録: 1〜100"] <--> B1["Instance2<br/>記録: 1〜100"]
    A1 <--> C1["Instance3<br/>記録: 1〜100"]
    B1 <--> C1
  end
  subgraph AFTER["Instance1 が閉鎖した後"]
    direction TB
    A2["Instance1<br/>（停止）"]
    B2["Instance2<br/>記録: 1〜100<br/>レートも同じ"] <--> C2["Instance3<br/>記録: 1〜100<br/>レートも同じ"]
  end
  BEFORE --> AFTER
```

- Instance2・Instance3 は、Instance1 が確定させた記録も含めて全記録を持っているため、**戦績もランキングもそのまま** です。
- 記録には両プレイヤーの署名が付いているので、Instance1 がいなくなった後でも、記録が本物かどうかを誰でも確かめられます。
- Instance1 の利用者が別のインスタンスで続けるための **アカウントの引っ越し**、閉鎖したインスタンスの記録を他のインスタンス経由で新しい参加者に渡す **再配布** は今後の実装です（→ [ロードマップ](../roadmap.md) Phase 3）。
