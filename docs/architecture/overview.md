# アーキテクチャ概要

> ステータス: **Draft**（議論中）。確定した判断は [ADR](../adr/README.md) に記録します。

## 1. 全体像

SmashHub は、独立した運営者が立てる複数の **インスタンス（サーバー）** が連携して1つの対戦ネットワークを形作る **連合型（federated）** システムです。インスタンス同士が対戦記録と対戦募集を共有することで、記録の消失を防ぐだけでなく、サイトごとにレートが分断されることや、利用者の少ないインスタンスでマッチングしないことを防ぎます（→ [ビジョン](../vision.md)、[図解](federation-walkthrough.md)）。

```mermaid
flowchart TB
  subgraph I1[インスタンス A]
    FE1[Frontend] --> BE1[Backend]
    BE1 --> DB1[(DB)]
  end
  subgraph I2[インスタンス B]
    FE2[Frontend] --> BE2[Backend]
    BE2 --> DB2[(DB)]
  end
  subgraph I3[インスタンス C / ミラー専用]
    BE3[Backend] --> DB3[(DB)]
  end
  P1((プレイヤー)) --> FE1
  P2((プレイヤー)) --> FE2
  BE1 <-- SmashHubプロトコル --> BE2
  BE2 <-- SmashHubプロトコル --> BE3
  BE1 <-- SmashHubプロトコル --> BE3
```

| 構成要素 | 役割 |
|---|---|
| Frontend | プレイヤー向け Web UI。自分のインスタンスの Backend とだけ通信する |
| Backend | アカウント管理・対戦募集・結果報告・レーティング・連合を担う |
| DB | アカウント情報（インスタンスローカル）と対戦記録（連合で共有）を保持 |
| ミラー専用インスタンス | 利用者を受け付けず、記録の保全のみを行う軽量な構成（任意） |

## 2. データの3分類

分散システムの設計で最も重要なのは「どのデータを、どこまで共有するか」です。SmashHub ではデータを3つに分けます。

| 分類 | 例 | 置き場所 | 共有 |
|---|---|---|---|
| **ローカルデータ** | 識別子ハッシュ（外部認証との紐づけ）、署名鍵（暗号化）、セッション、通知設定、対戦設定（拒否ステージ・スイッチ・マッチング条件・配信 / 動画化）、ブロック | ホームインスタンスのみ | しない |
| **一時データ** | 対戦募集（マッチング待ち）、対戦ルームのメッセージ | 募集を出したインスタンス | 必要な相手とだけ、その場限り |
| **永続共有データ** | アカウントの公開情報（ID・公開鍵・表示名）、確定した対戦記録 | 連合内の全インスタンス | **する（複製）** |

- 各データの保持期間と公開範囲の詳細は [データ保護](../security/data-protection.md) を参照してください。
- **個人情報はどの分類にも含めません。** ログインは外部の認証プロバイダーに任せます（→ [認証](../security/authentication.md)、[データ保護](../security/data-protection.md)）。
- **レーティングはどこにも「保存の正」がありません。** 永続共有データである対戦記録から計算される **派生データ** です（→ [レーティング](../domain/rating.md)）。
- 永続共有データは小さく保ちます。1件の対戦記録は 1KB 程度を想定しており、100万件でも 1GB 程度です。これにより「全インスタンスが全記録を持つ」完全複製が現実的になります。

## 3. 信頼のモデル

連合では、他のインスタンスの運営者を無条件には信頼できません。SmashHub は「運営者を信頼しなくても記録の正しさを検証できる」ことを目指します。

### 3.1 アカウント ID と鍵

- 各アカウントは **署名鍵ペア** を持ち、アカウント ID は公開鍵から導出します（Ed25519 公開鍵の `did:key`。→ [ADR 0008](../adr/0008-account-id-did-key.md)）。
- 表示用には `@name@instance.example` 形式のハンドルを使いますが、これはホームインスタンスが変わると変わる「住所」であり、アカウントの同一性は鍵に基づく ID で判断します。
- 当初は鍵をホームインスタンスが管理します（利用者が鍵を意識しなくてよいように）。
- アカウント作成時に **リカバリーキー** を発行し、利用者が手元に保管します。ホームインスタンスが突然消えても、リカバリーキーで別インスタンス上にアカウントを復元できます（→ ロードマップ Phase 3）。

### 3.2 対戦記録の署名

- 対戦記録は **対戦した両プレイヤーの署名** がそろって初めて「確定」します。両プレイヤーがそれぞれ結果を報告し、報告が噛み合った時点で両者の署名がそろいます。24時間で噛み合わなければ確定せず、記録も作りません（→ [対戦ルール](../domain/match-rules.md)）。
- 署名済みの記録は、どのインスタンスを経由して届いても内容が改ざんされていないことを検証できます。
- 加えて、記録を最初に受け付けたインスタンスが自身の署名を付け、ログに追記します（→ [SmashHubプロトコル](federation.md)）。

### 3.3 インスタンス間の信頼

- 署名で守れるのは「改ざん」までです。「架空のアカウント同士の架空の対戦（自作自演）」は署名だけでは防げません。
- そのため、インスタンス単位の **連合ポリシー（許可リスト/拒否リスト）** と、[サーバー運用者の約束事](../operations/server-covenant.md) への同意を連合参加の条件とします。
- レート操作対策は [レーティング](../domain/rating.md) の「不正対策」で扱います。

## 4. 主要なユースケースの流れ

### 4.1 同一インスタンス内の対戦

```mermaid
sequenceDiagram
  actor A as プレイヤーA
  actor B as プレイヤーB
  participant S as インスタンス
  A->>S: 対戦相手を探す（条件に合う募集がなければ A の募集になる）
  B->>S: 対戦相手を探す → A の募集とマッチング成立
  Note over A,B: ゲーム内で対戦（部屋ID等は SmashHub上で共有）
  A->>S: 結果を報告（Aが署名）
  B->>S: 結果を報告（Bが署名）
  S->>S: 報告が噛み合えば記録を確定し、ログに追記
  S-->>S: レート再計算
  S->>S: 連合先へ記録を配信
```

### 4.2 インスタンスをまたぐ対戦

待機中の対戦募集を連合先に配り合い、別のインスタンスの利用者ともマッチングします。先に待っていた側のインスタンスが対戦の **ホスト** となり、結果報告の受付と確定を担当します。相手プレイヤーはホームインスタンス経由で結果報告（署名）を送ります。流れは [SmashHubプロトコル](federation.md) の 11.4 と [図解](federation-walkthrough.md) の「5. インスタンスをまたぐ対戦」を参照してください。

### 4.3 インスタンス閉鎖時

1. 閉鎖するインスタンスは閉鎖予告を連合へ配信する（予告機能は Phase 3）。
2. 利用者は別インスタンスへアカウントを移行する。
3. 閉鎖後も、そのインスタンスで確定した記録は他インスタンスに複製済みのため失われない。
4. 予告なく消えた場合でも、記録は複製済み、アカウントはリカバリーキーで復元できる。

## 5. 決定済みの事項

- 対戦記録の連合は独自プロトコルで行う（[ADR 0006](../adr/0006-custom-federation-protocol.md)）
- 連合には営利・非営利を問わず参加できる。SmashHub プロジェクト自身は非営利（[ADR 0011](../adr/0011-federation-participation-conditions.md)）
- アカウント ID は Ed25519 公開鍵の did:key（[ADR 0008](../adr/0008-account-id-did-key.md)）
- レートは連合全体で1つ（SmashHubレート）。インスタンスごとのレートは設けない（[レーティング](../domain/rating.md)）
