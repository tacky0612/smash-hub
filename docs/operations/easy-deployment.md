# 技術者でなくてもインスタンスを立てられるようにする

> ステータス: **決定済み**。国内 VPS のスタートアップスクリプトで立ち上げる方式に決まりました（[ADR 0009](../adr/0009-deployment-vps-startup-script.md)）。以下は議論の記録です（議論: [#1](https://github.com/tacky0612/smash-hub/issues/1)）。

## 1. 背景

SmashHub のインスタンス運営者として想定しているのは、IT 技術者ではなく **スマブラのファン** です。
分散システムは「運営者が増えること」で初めて価値を持ちます。立ち上げに専門知識が必要だと運営者が増えず、結局一部の技術者に負担が集中してしまいます。これはスマメイトが閉鎖したのと同じ構図です。

そのため「技術的な知識をあまり必要とせずにデプロイ・運用できること」を要件とし、その実現方法を議論して決めます。

## 2. 想定する運営者像（たたき台）

- スマブラのコミュニティ（地域コミュニティ・配信者・サークル等）の世話役
- PC やスマートフォンの操作には慣れている。Discord サーバーの管理くらいはできる
- ターミナル（黒い画面）、SSH、Linux、DNS、TLS 証明書の知識は **ない前提**
- 月数百円〜千円程度の費用なら自己負担できる（無料が望ましい）
- 運営に使える時間は月に数時間程度

## 3. 決めること

1. **ターゲットとする運営者のスキルの下限** — 上の運営者像でよいか
2. **主たるデプロイ方式** — 後述の選択肢からどれを「公式に推奨する手順」とするか
3. **運営者の費用の上限** — 無料が必須か、月額いくらまでを許容するか（[非営利の方針](../policy.md) との関係も含む）
4. **初期設定で運営者にやってもらうこと** — ドメイン取得・Discord アプリ登録などをどこまで減らせるか
5. **運用中に運営者にやってもらうこと** — アップデート・バックアップ・障害対応をどこまで自動化するか
6. **インスタンスの種類ごとの手順** — 「フル機能のインスタンス」と「記録を保全するだけのミラー」で手順を分けるか
7. **技術選定への要求** — 上の結論から、言語・DB・ランタイムに課す条件（→ [技術選定](../tech-selection.md)）

## 4. 検討する選択肢（たたき台）

| # | 方式 | 運営者の作業 | 長所 | 懸念 |
|---|---|---|---|---|
| A | **VPS + Docker Compose + セットアップスクリプト** | VPS を借りて SSH でコマンドを数行実行 | 自由度が高い。費用が安定 | SSH・ターミナルが必要で、想定運営者には難しい |
| B | **VPS 事業者のテンプレート / スタートアップスクリプト**（国内 VPS のアプリテンプレート、1-Click アプリ等） | VPS の申込画面で SmashHub を選ぶ | ブラウザ操作だけで完結しうる | 事業者ごとに登録・保守が必要。事業者側の掲載審査 |
| C | **PaaS のワンクリックデプロイ**（Deploy ボタン） | ボタンを押してアカウント連携 | 操作が最も少ない。HTTPS 自動 | 無料枠の縮小・料金改定に左右される。DB の永続化 |
| D | **サーバーレス / エッジの無料枠**（Workers + サーバーレス DB 等） | アカウント作成とデプロイ操作 | 無料で、サーバー管理が実質不要 | 特定事業者への依存。実装の制約が大きく、技術選定に強く影響する |
| E | **自宅の PC / Raspberry Pi + トンネル** | アプリをインストールして起動 | 追加費用がほぼゼロ | 常時稼働・停電・回線の問題 |
| F | **GitHub の fork + GitHub Actions / Pages**（ミラー専用） | リポジトリを fork して Actions を有効にする | 無料。サーバー不要で記録の保全に参加できる | 閲覧・保全のみで、フル機能のインスタンスには使えない |

組み合わせ案の例: **フル機能は B または C、ミラーは F** で入口を広げ、技術に詳しい人向けに A も残す。

### どの方式でも必要になりそうな工夫

- **管理画面での設定** — 設定ファイルや環境変数を編集させず、初回起動時のブラウザのセットアップ画面で設定できるようにする
- **HTTPS の自動化** — 証明書の取得・更新を自動にする
- **ドメイン** — 独自ドメインを必須にするか、無料のサブドメインを使えるようにするか
- **Discord アプリ登録のガイド** — 画面ごとの手順書（[認証](../security/authentication.md)）
- **自動アップデート** — 管理画面からワンクリック、またはセキュリティ更新の自動適用
- **自動バックアップ** — DB と秘密情報（鍵・ペッパー）のバックアップを、手元にダウンロードできる形で定期作成する
- **ヘルスチェックと通知** — 異常時に運営者の Discord へ通知する
- **閉鎖の手順もワンクリックで** — 閉鎖予告・最終複製を管理画面から実行できるようにする

## 5. 評価基準（案）

| 基準 | 内容 |
|---|---|
| 必要な知識 | ターミナル操作・SSH・DNS の知識が要らないか |
| 立ち上げ時間 | 手順書を見ながら 30 分程度で公開まで到達できるか |
| 費用 | 無料、または月額の上限以内か |
| 継続性 | 事業者の料金改定・サービス終了に耐えられるか（逃げ道があるか） |
| 運用の手間 | アップデート・バックアップ・証明書更新が自動か |
| セキュリティ | 安全な初期設定のまま運用できるか（→ [セキュリティポリシー](../security/README.md)） |
| 開発への影響 | 実装・テストが過度に複雑にならないか |

## 6. 進め方

1. 運営者像（2.）について、実際に運営してくれそうなコミュニティの人に意見を聞く
2. 選択肢を評価基準で比較する
3. 有力な方式で、技術者でない人に試してもらう（ユーザーテスト）
4. 結論を ADR にまとめ、[技術選定](../tech-selection.md) の条件に反映する

## 7. 完了条件

- 主たるデプロイ方式と、運営者の費用・スキルの前提が ADR として `Accepted` になっている
- 技術選定の選定基準に、この結論が反映されている
