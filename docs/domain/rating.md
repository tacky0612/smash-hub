# レーティング

> ステータス: **Draft**。

## 1. 要件

| 要件 | 理由 |
|---|---|
| **決定的であること** | 同じ対戦記録の集合からは、どのインスタンスで計算しても同じレートになること。これが「レートを運営者に依存させない」ための前提 |
| **記録の到着順に依存しないこと** | 連合では記録が届く順番がインスタンスごとに異なる。届く順でレートが変わってはいけない |
| **再計算できること** | レートは保存の正ではなく派生データ。記録が追加・無効化されたら作り直せる |
| **分かりやすいこと** | プレイヤーが「なぜこのレートなのか」を理解できること |

## 2. 算出方式（案）

### 2.1 アルゴリズム

**Glicko-2** を第一候補とします。

- Elo は1試合ごとに逐次更新するため、記録の順番に結果が強く依存します。
- Glicko-2 は **レーティング期間** 単位でまとめて更新するため、期間内の記録の並び順に依存しません。また、対戦頻度の少ないプレイヤーの不確かさ（RD）を表現できます。
- 表示用のレートは、従来のサイトの利用者になじみのあるスケール（例: 1500 起点）に合わせます。

### 2.2 決定性を守るための約束

1. **期間の締め** — レーティング期間（例: 日本時間で1日）ごとにレートを更新する。期間は `played_at`（対戦開始日時、両者の署名対象）で決める。
2. **遅れて届いた記録** — 締めた期間に属する記録が後から届いた場合、その期間から再計算する。再計算の対象を限定するため、一定期間（例: 7日）を過ぎた期間は **確定（ファイナライズ）** とし、それ以降に届いた古い記録はレート計算に含めない（記録自体は保存する）。
3. **数値計算** — 浮動小数点の演算結果が言語や CPU で変わらないよう、固定小数点演算または計算手順・丸めの厳密な規定を行う。参照実装とテストベクタ（入力記録と期待するレートの組）をリポジトリで管理する。
4. **バージョン管理** — 算出方式やパラメータを変えるときは「レート方式のバージョン」を上げ、シーズンの区切りでのみ切り替える。

```mermaid
flowchart LR
  R[(対戦記録の集合)] --> F[フィルタ<br/>レートスコープ・無効化・シーズン]
  F --> G[期間ごとに分割<br/>played_at 基準]
  G --> C[Glicko-2 で期間ごとに更新<br/>決定的な計算]
  C --> O[レート・ランキング]
```

## 3. レートスコープ

連合ポリシーによって、インスタンスごとに取り込む記録の範囲が異なる場合があります。そのためレートは「どの範囲の記録で計算したか」を伴って表示します。

| スコープ | 内容 |
|---|---|
| **連合レート**（標準） | 連合ポリシーで許可しているすべてのインスタンスの記録で計算 |
| **インスタンスレート** | 特定インスタンスがホストした対戦のみで計算（ローカル大会・コミュニティ向け） |

標準的な連合ポリシーを共有しているインスタンス同士では、連合レートは一致します。

## 4. 不正対策

署名で防げるのは改ざんまでで、レート操作は別途対策が必要です。

| 手口 | 対策（案） |
|---|---|
| 複数アカウントの自作自演 | 新規アカウントの RD を大きく取り、ランキング掲載に最低対戦数・最低対戦相手数を設ける。同一相手との連戦はレート変動を逓減させる |
| 架空アカウントを量産するインスタンス | 連合ポリシー（許可リスト）と運用者の約束事。問題のあるインスタンスは拒否し、その記録をレート計算から除外 |
| 虚偽の結果報告 | 両者の報告が噛み合った場合のみ確定。噛み合わなければ24時間でレート変動なしで終了 |
| 談合（八百長） | 異常検知（短期間の同一ペア偏重など）とモデレーションによる無効化 |

## 5. 対戦ルールとの関係

- レートは **対戦（BO3）単位** で更新します。ゲーム単位の勝敗は記録しますが、レート計算には使いません。
- レート計算の対象は [標準ルール](match-rules.md) で行われた対戦のみとします。
