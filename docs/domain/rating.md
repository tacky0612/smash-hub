# レーティング

> ステータス: **Draft**。計算式は **スマメイト式**（スマメイトの実際のレート変動に一致する式）を採用します。

## 1. 要件

| 要件 | 理由 |
|---|---|
| **決定的であること** | 同じ対戦記録の集合からは、どのインスタンスで計算しても同じレートになること。これが「レートを運営者に依存させない」ための前提 |
| **記録の到着順に依存しないこと** | 連合では記録が届く順番がインスタンスごとに異なる。届く順で最終的なレートが変わってはいけない |
| **再計算できること** | レートは保存の正ではなく派生データ。記録が追加・無効化されたら作り直せる |
| **分かりやすいこと** | プレイヤーが「なぜこのレートなのか」を理解できること。スマメイトの利用者になじみのある動き方をすること |

## 2. 計算式（スマメイト式）

### 2.1 1回の対戦での変動

対戦（BO3）1回ごとに、勝者と敗者の **対戦前のレート** から変動値 `Δ` を求めます。レートは **整数** です。

```
Δ = floor( 16 + (敗者のレート − 勝者のレート) ÷ 25 )
Δ = min( max(Δ, 1), 30 )          # 最小 1・最大 30

勝者の新しいレート = 勝者のレート + Δ
敗者の新しいレート = max( 敗者のレート − Δ, 1000 )   # 1000 より下がらない
```

- 同じレート同士なら ±16。レート差 25 ごとに変動が 1 ずつ変わります。
- 格上に勝つほど多く上がり、格下に負けるほど多く下がります。
- 敗者が 1000 で止まった場合も、勝者は通常どおり `Δ` 上がります。

| 相手が 375 以上下 | +1 | −1 |

### 2.3 整数演算の規定

浮動小数点を使わず、整数演算だけで計算します。これにより言語・環境による差が出ません。

```
d = 敗者のレート − 勝者のレート      # 整数（負の値もとる）
Δ = floor_div(400 + d, 25)          # 負の数は −∞ 方向に丸める（floor division）
Δ = min( max(Δ, 1), 30 )
```

- `floor_div` は負の数を **−∞ 方向** に丸めます。0 方向に丸める言語（C 系の `/` 等）では補正が必要です。例: `floor_div(−489, 25) = −20`（0 方向の丸めでは −19）。
- 負になるのは最小値 1 に切り上げられる範囲だけなので結果には影響しませんが、実装の食い違いを防ぐため規定しておきます。

## 3. シーズン

- レートは **シーズンごと** に集計します。シーズンは **メインシーズンのみ** とし、**シーズン開始時は全員 1500** から始めます。
- シーズン最初の数戦だけ変動を大きくする仕組み（置き戦）は **設けません**。
- シーズンの長さは **約2か月**（年6回）です。具体的な開始・終了日時はプロジェクトで告知し、全インスタンスで共通の日時（日本時間）で切り替えます。
- スマメイト等、他サービスの過去のレートは **引き継ぎません**。

## 4. 決定性を守るための約束

スマメイト式は対戦ごとに逐次更新するため、**対戦を処理する順番** で結果が変わります。連合のどのインスタンスでも同じ結果になるよう、次のように定めます。

1. **処理の順番** — シーズン内の確定した対戦記録を、`played_at`（対戦開始日時。両者の署名対象）の昇順、同時刻の場合は記録 ID（記録内容のハッシュ）の昇順で並べ、先頭から順に適用する。到着した順番は使わない。
2. **遅れて届いた記録** — 既に計算済みの対戦より前の `played_at` を持つ記録が届いた場合は、その時点から後を再計算する。
3. **取り込みの締め切り** — ホストインスタンスがログに追記した日時（ホストの署名対象）と `played_at` の差が **7日** を超える記録はレート計算に含めない（記録自体は保存する）。どのインスタンスでも同じ値で判定できるため、取り込む記録の集合が一致する。
4. **暫定レートと確定レート** — 対戦直後のレートは、その時点で届いている記録から計算した **暫定レート** として即時に表示する。`played_at` から 7日以上経過した範囲は **確定** とし、以後は変わらない。通常は記録が数秒〜数分で行き渡るため、暫定レートと確定レートは一致する。
5. **無効化** — モデレーションで無効化（`MatchVoided`）された記録は除外し、その記録の `played_at` から後を再計算する。
6. **バージョン管理** — 計算式やパラメータを変えるときは「レート方式のバージョン」を上げ、シーズンの区切りでのみ切り替える。

```mermaid
flowchart LR
  R[(確定した対戦記録)] --> F[フィルタ<br/>シーズン・連合ポリシー<br/>無効化・取り込みの締め切り]
  F --> S[played_at → 記録 ID の順に並べる]
  S --> C[スマメイト式で1件ずつ適用<br/>整数演算]
  C --> O[レート・ランキング]
```

## 5. 表示とランキング

- 表示するのは **レートの値そのもの** です。レートはプレイヤー単位のみとし、ファイター別のレートは提供しません（使用ファイターごとの戦績は統計として表示します）。
- ランキングに掲載するのは、そのシーズンに **20戦以上** 対戦したプレイヤーです。
- 対戦中止・報告の食い違い・期限切れの対戦ではレートは変動しません（→ [対戦ルール](match-rules.md)）。

## 6. 連合レート

**レートは連合全体で1つ（連合レート）だけ** とし、インスタンスごとのレートは設けません。サイトごとにレートが分かれると、同じレートでもサイトによって強さの水準が違い、プレイヤー同士で比べられなくなるためです（→ [ビジョン](../vision.md) の「記録とレートの分断」）。

- 各インスタンスは、自分がホストした対戦の記録と、連合先から取り込んだ記録のすべてを使って、同じ手順で連合レートを計算します。
- ランキングも連合レートで作ります。どのインスタンスで見ても同じ順位になります。
- 「このインスタンスでの戦績」のような表示は、レートではなく統計として扱います。
- プロトコルを独自に実装して連合に参加するサイトは、サイト独自のレート（サイトの中だけのレートや、別の計算式によるレート）を併用してかまいません。ただし、利用者が「レート」と見て連合レートと取り違えないよう、独自のレートは連合レートと区別できる別の名前で表示します。
- 連合ポリシーで拒否したインスタンスの記録は計算に含めないため、拒否リストが違うとインスタンスによって値がずれます。参加インスタンスは共通の拒否リストを使うことを推奨します（[連合プロトコル](../architecture/federation.md) の「9. 連合ポリシー」）。

## 7. 不正対策

署名で防げるのは改ざんまでで、レート操作は別途対策が必要です。

| 手口 | 対策 |
|---|---|
| 複数アカウントの自作自演 | 外部プロバイダーの1アカウントにつき1アカウント（→ [認証](../security/authentication.md)）。ランキング掲載は20戦以上。連戦を避けるマッチング条件 |
| 架空アカウントを量産するインスタンス | 連合ポリシー（許可リスト）と運用者の約束事。問題のあるインスタンスは拒否し、その記録をレート計算から除外 |
| 虚偽の結果報告 | 両者の報告が噛み合った場合のみ確定。噛み合わなければ24時間でレート変動なしで終了 |
| 談合（八百長） | 異常検知（短期間の同一ペア偏重など）とモデレーションによる無効化 |

## 8. 対戦ルールとの関係

- レートは **対戦（BO3）単位** で更新します。ゲーム単位の勝敗は記録しますが、レート計算には使いません。
- レート計算の対象は [標準ルール](match-rules.md) で行われた対戦のみとします。
