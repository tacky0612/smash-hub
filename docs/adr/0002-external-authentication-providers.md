# 0002: 認証に外部プロバイダー（Discord / Google）を使い、個人情報を保持しない

- ステータス: Accepted
- 日付: 2026-10-26

## 背景

- インスタンスは個人運営を前提としており、運用負荷を小さくしたい。
- インスタンスに個人情報を保持しない方針とする（漏えい時の被害と、運営者の責任を小さくするため）。
- 認証の仕組みは無料で利用でき、インスタンス運営者が自分で設定できる必要がある。

## 検討した選択肢

1. **パスワード認証（自前）** — 外部依存はないが、パスワードとメールアドレスの保持・保護が運営者の責任になる。
2. **自前の認証基盤（Keycloak 等）** — 柔軟だが運用負荷が大きい。
3. **認証 SaaS（Auth0・Clerk・Firebase Authentication 等）** — 無料枠はあるが、利用者数の上限や料金体系の変更に左右される。個人情報を SaaS 側に預ける構成になりやすい。
4. **ソーシャルログインを直接使う（OAuth 2.0 / OIDC）** — 無料で、利用者数の上限がない。受け取る情報をスコープで最小限にできる。

## 決定

選択肢 4 を採用する。

- **Discord**（OAuth 2.0, `identify` スコープ）を標準のプロバイダーとする。
- **Google**（OpenID Connect, `openid` スコープ）を任意で有効にできるプロバイダーとする。
- プロバイダーの利用者 ID はインスタンスごとのペッパーで HMAC した **識別子ハッシュ** としてのみ保存する。ユーザー名・メールアドレス・トークンは保存しない。
- X (Twitter) は API の利用条件・料金体系の変更が多いため、当面採用しない。

## 理由

- 運営者は各プロバイダーにアプリを無料で登録するだけでよく、認証サーバーを運用する必要がない。
- Discord はスマブラのコミュニティで広く使われており、利用者の登録の手間が小さい。
- 最小限のスコープとハッシュ化により、インスタンスが個人情報を保持しない設計を実現できる。
- 連合内のアカウントの同一性は鍵に基づく ID で表すため、認証プロバイダーの選択は SmashHubプロトコルに影響しない。

## 影響

- 利用者は Discord か Google のアカウントが必要になる。
- プロバイダーの規約変更・障害の影響を受ける。複数プロバイダーの紐づけとリカバリーキーで緩和する。
- 個人情報を持たないため、複数アカウントの防止は完全にはできない（→ [認証](../security/authentication.md) の「複数アカウント対策との関係」）。
- 外部に依存しないパスキー（WebAuthn）の追加を将来再検討する。

詳細は [認証](../security/authentication.md)・[データ保護](../security/data-protection.md) を参照。
