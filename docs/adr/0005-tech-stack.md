# 0005: フロントエンドを React（SPA）、バックエンドを Go、DB を PostgreSQL とする

- ステータス: Accepted
- 日付: 2026-10-26

## 背景

- 対戦の一連の流れ（ログイン → マッチング → 結果報告 → レート反映）が動くものを早く作り、コントリビューターが触れる状態にしたい。
- [技術選定](../tech-selection.md) の基準（運用の軽さ・コントリビューターの集まりやすさ・型安全性・暗号ライブラリの品質・クリーンアーキテクチャとの相性・決定的な計算）を満たす必要がある。
- 技術者でない運営者向けのデプロイ方式（[#1](https://github.com/tacky0612/smash-hub/issues/1)）は議論中だが、どの方式でもコンテナで動かせる構成にしておく。

## 決定

| 対象 | 採用 |
|---|---|
| フロントエンド | React（SPA）+ TypeScript + Vite + React Router。ビルド結果を静的ファイルとして nginx で配信する |
| バックエンド | Go（標準ライブラリの `net/http`）、DB ドライバーは pgx |
| データストア | PostgreSQL |
| ローカル環境 | Docker Compose（web / backend / db、結合テスト用の db-test） |

## 理由

- **Go** — 単一バイナリで配布でき、メモリ消費が小さく、個人の VPS 1台でも運用が軽い。暗号（HMAC・Ed25519）が標準ライブラリで揃う。インターフェースによる依存逆転が書きやすく、`internal/` でモジュール境界を守れる。
- **React（SPA）** — コントリビューターが最も多い。SPA は静的ファイルとして配信でき、サーバー側の実行環境が要らない。
- **PostgreSQL** — 信頼性が高く、行ロック（`FOR UPDATE SKIP LOCKED`）でマッチングの同時実行を安全に扱える。Docker で結合テストを再現しやすい。

## 影響

- リアルタイム通知は当面ポーリング（3秒間隔）で実装する。必要になれば SSE / WebSocket に置き換える。
- SQLite への対応は、デプロイ方式の議論（#1）の結論次第で、リポジトリ層の実装を追加して検討する。
- 依存ライブラリは AGPL-3.0 と互換性のあるライセンスに限る（React・React Router・Vite: MIT、pgx: MIT）。
