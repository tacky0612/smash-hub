# 0008: アカウント ID は Ed25519 公開鍵の did:key とする

- ステータス: Accepted
- 日付: 2026-10-27

## 背景

- 連合の中でアカウントの同一性を、インスタンスやハンドル（`@name@instance`）に依存せずに表す必要がある（引っ越しても過去の対戦記録と同一人物として結びつけるため）。
- 対戦記録・アカウントの公開情報には、アカウント自身の署名が必要で、受け取った誰もがその署名を検証できなければならない（[連合プロトコル](../architecture/federation.md) 4.3）。
- 連合全体で調整しなくても、ID が重複しないこと。

## 検討した選択肢

1. **did:key（公開鍵そのものから ID を作る）** — ID から公開鍵が分かるため、追加の問い合わせなしに署名を検証できる。鍵を更新すると ID が変わる。
2. **did:plc 類似の方式（最初の鍵から作った ID に、鍵の更新履歴をひもづける）** — 鍵を更新しても ID が変わらない。更新履歴を管理・配布する仕組みが別に必要。
3. **インスタンスが発行する独自 ID** — 単純だが、ID と鍵の結びつきを発行元のインスタンスに頼ることになる。

## 決定

アカウント ID は、Ed25519 公開鍵の **did:key**（`did:key:z` + base58btc(multicodec `0xed01` + 公開鍵)）とする。

## 理由

- ID だけで署名を検証でき、インスタンスを信頼しなくてよい（自己証明型）。
- 連合全体で調整しなくても重複しない。
- 仕組みが小さく、実装・検証が容易（現在の実装で採用済み）。

## 影響

- 鍵を更新（`AccountKeyRotated`）すると ID が変わる。過去の記録との結びつけ方（旧 ID から新 ID への引き継ぎ、リカバリーキーによる署名）は、鍵の更新を実装するときに決める（[アーキテクチャ概要](../architecture/overview.md) の未解決の論点）。
- 当初は利用者の秘密鍵をホームインスタンスが暗号化して預かる（[脅威モデル](../security/threat-model.md) 3.5）。
