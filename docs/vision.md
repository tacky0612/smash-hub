# ビジョン

## ミッション

**スマブラを楽しむプレイヤーの対戦の場と記録を、特定の誰かに依存せずに守り続ける。**

## 解決したい課題

対戦レーティングサイトは、プレイヤーにとって「対戦相手を見つける場」であると同時に「自分の歩みの記録」でもあります。しかし個人運営のサイトでは次の問題が避けられませんでした。

1. **単一障害点** — 運営者の事情（負担・費用・生活の変化）でサービスが終わる。
2. **記録の消失** — サービス終了と同時に、何年分もの対戦履歴やレートが消える。
3. **負担の集中** — サーバー費用、障害対応、不正対応、問い合わせ対応が1人に集まり、それ自体が閉鎖の原因になる。

## Smash-hub の答え

| 課題 | アプローチ |
|---|---|
| 単一障害点 | 複数の独立した運営者がサーバーを立て、相互に連携する（連合） |
| 記録の消失 | 対戦記録を複数サーバーへ複製する。記録は署名付きなので、どこに置かれていても本物か検証できる |
| 負担の集中 | 1台あたりの規模を小さく保ち、運営者・開発者を OSS コミュニティで分担する |

## 設計原則

1. **記録が主、サーバーは従** — 対戦記録は特定のサーバーではなくコミュニティ全体の資産。サーバーは記録を保持・中継する器にすぎない。
2. **誰でも検証できる** — 記録は両プレイヤーの署名付き。レートは記録から決定的に再計算できる。運営者を信頼しなくても正しさを確認できる。
3. **小さく運用できる** — 個人が安価な VPS 1台で運用できることを前提にする。重い依存やスケールアウト前提の構成を避ける。
4. **やめやすく、引き継ぎやすい** — 運営者がやめるときに、データと利用者を他のサーバーへ引き継げる手順をソフトウェアとして用意する。
5. **スモールスタート** — 最初から完全な分散システムを目指さない。単一サーバーで価値を出しつつ、データ設計だけは最初から分散前提にする（→ [ロードマップ](roadmap.md)）。

## やらないこと（Non-goals）

- **収益化** — 広告・有料機能・課金は実装しない（→ [運営ポリシー](policy.md)）。
- **公式素材の利用** — 任天堂の利用許可が出ている素材以外は使わない。
- **ブロックチェーン / 暗号通貨** — 改ざん検知には電子署名とハッシュチェーンで十分であり、トークンや手数料の仕組みは持ち込まない。
- **大会運営プラットフォーム** — 当面は「野良対戦のマッチングとレーティング」に集中する。大会機能は将来の検討事項とする。
- **ゲームとの直接連携** — ゲーム本体やネットワークへの解析・改変・自動化は行わない。対戦はプレイヤーがゲーム内で行い、結果は人が報告する。

## 成功の定義

- 最初の運営者がいなくなっても、サービスと対戦履歴が継続している。
- 3つ以上の独立した運営者によるサーバーが連携して稼働している。
- 運営者が1人で抱える作業が「サーバーを動かし続けること」程度に収まっている。
